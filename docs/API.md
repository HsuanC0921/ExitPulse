# API 執行方式與效能

API 是 FastAPI 應用，程式在 `apps/api/`，在專案根目錄啟動：

```bash
uvicorn main:app --app-dir apps/api --host 127.0.0.1 --port 5011
```

連線字串讀 `EXITPULSE_DATABASE_URL`，互動式文件在 `http://127.0.0.1:5011/docs`。

## 結構

| 檔案 | 責任 |
| --- | --- |
| `main.py` | 路由、參數驗證、把分析結果對應成 HTTP 回應，並啟用 gzip |
| `runner.py` | 分析行程池、結果快取、相同請求合併、排隊上限與逾時 |
| `places.py` | 地圖的地點搜尋，轉送 Photon，限速並快取 |

分析本身在 `tools/`（`query_od.py`、`analyze_od.py`、`station_info.py`、`od_postgres.py`）。`runner.py` 啟動 2 個行程，每個行程自帶資料庫連線池，用 `tools/od_worker.dispatch` 在行程內執行查詢，所以一次請求不必重啟 Python，也不必重連資料庫。

## 行為

- 相同條件同時進來只跑一次，等待的請求共用結果。
- 結果快取：目錄類查詢（已匯入月份、各站可用日期、查詢目錄）5 秒，其餘 2 分鐘，最多 1024 筆。
- 預設同時執行 2 個分析，另可有 40 個分析排隊。等待回應的呼叫數和未完成的分析數各設上限，額滿回 429。所有呼叫者都離開後，排隊中的分析會取消。
- 等待分析預設 30 秒，逾時回 504。調整 `EXITPULSE_WORKERS`、`EXITPULSE_QUEUE_LIMIT`、`EXITPULSE_TIMEOUT_SECONDS` 可改預設值。API 行程池另設 PostgreSQL `statement_timeout`，預設沿用 API 逾時。用 `EXITPULSE_SQL_TIMEOUT_SECONDS` 可縮短單一 SQL 敘述的上限。
- 分析腳本的結束碼對應 HTTP：2 回 422（無法比較），3 回 404（月份未匯入），4 回 422 `unrecorded_hours`，5 回 422 `hours_mismatch`（帶 `recordedHours` 與 `suggested`），其他回 503。
- 回應內容就是分析腳本輸出的 JSON，API 不重新序列化。

## 榜單與日型

`GET /api/v1/od/leaders?period=2026-09&compare=2022-09&days=weekday&start=7&end=10&limit=10`

- `period` 必填，`compare`、`days`（`weekday`、`workday`、`weekend`、`all`）、`start`、`end`、`limit`（1 至 20，預設 10）可省略。
- 回傳 `busiestStations`（站、每日進站、每日出站）與 `busiestPairs`（起、迄、每日人次，不含同站進出）。
- 有 `compare` 時另有 `risingStations` 與 `fallingStations`（站、對照期、本期、增減、成長百分比）。只列兩期都同時有進站與出站紀錄、對照期每日進站量至少 200、且不是站名口徑未確認的轉乘站，規則與站對比較一致。
- `workday` 與 `weekday` 的差別：`weekday` 是週一至週五，不扣國定假日。`workday` 依行事曆排除國定假日，並把補班日算進來。兩站比較（`/od/radar`、`/od/pair`）同樣支援 `days=workday`（不可與 `weekend=true` 同時傳入），回應會帶 `daysType: "workday"`。
- 工作日月查詢以週一至週五的既有彙總為底，扣掉放假日並加上補班日。例外日過多時直接加總選定日期。每個分析行程依資料來源雜湊與有效工作日快取最多 24 組彙總，供單站、全網與榜單共用。使用 `python tools/stress_api.py --mode workday` 可測這三種查詢的混合負載。

## 出站資料涵蓋

`/od/station` 的回應與 `/od/network` 的回應及各站資料都有 `exitCovered`。指定對照期時，另有 `compareExitCovered`，否則省略。兩個欄位各自依該期已匯入資料的目的站名單判定，站名沿用 OD 查詢的轉乘站合併規則。有分段涵蓋紀錄時，車站須出現在所有與查詢日期重疊的目的站名單中。全網回應的頂層欄位代表該期所有車站都有出站涵蓋。

`false` 代表出站資料涵蓋不足。原有 `exits` 和逐時欄位維持相容，其中的 0 可能來自彙總補零。2020 年 1 月及 2023 年 5 月至 2026 年 9 月的匯入資料，共有十個環狀線車站在一個以上月份出現這種情況。介面判讀出站量、進出比例或淨流量前，應先檢查涵蓋欄位。

互搭表 `/od/matrix` 另提供 `missingOrigins` 和 `missingDestinations`。兩份名單都只包含該張表的車站。缺少起站或訖站涵蓋的格子會標示「資料不足」，原始數值陣列 `cells` 維持相容。

## 站群旅次

`GET /api/v1/od/group-flow?period=2026-09&origin=台北車站&origin=市政府&destination=西門&destination=亞東醫院&start=7&end=10`

`origin` 和 `destination` 可重複傳入。各群至少一站，合併轉乘站別名後去除重複站名。起訖群組可重疊，選到的同站旅次也納入。可選的 `compare`、`days`、`start`、`end` 沿用單站查詢的定義。

回應的 `current` 與 `compare` 各自提供期間、平均每日人次 `daily`，以及 `missingOrigins` 和 `missingDestinations`。任一清單有缺漏時，該期的 `daily` 為 `null`。完整涵蓋且沒有旅次時回 0。省略比較期時，`compare` 為 `null`。

### 逐時旅次分組儲存（2026-11-19）

切換前本機 PostgreSQL 約 50 GiB，其中約 32 GiB 是資料表、18 GiB 是索引。逐時原始 `trips` 約占 36 GiB。每個站對原本各用一列，分組版改為每天、每小時、每起站一列，同列保存對齊的目的站代號與人次陣列。日期及時段仍可用主鍵找出，查詢時再展開陣列。

| 匯入月份 | 逐時資料列 | 舊表＋索引 | 分組暫存表＋索引 |
|---|---:|---:|---:|
| 2020-12 | 5,585,911 | 356.0 MiB | 41.6 MiB |
| 2026-09 | 5,105,454 | 325.2 MiB | 38.1 MiB |

兩個月的總列數及總人次相同，抽驗日期的逐站對加總完全一致。2026-09 單日 07–10 時段在同一連線測三次，舊表約 13–16 毫秒，分組表約 17–19 毫秒。2020-12 選三天的加總約為 30–39 毫秒及 32–40 毫秒。

正式切換已完成。2017-01 至 2026-09 共 117 個月，逐筆比對 586,700,961 筆站對及人次。每月日期、時段、站點涵蓋和原始站名對照均與切換前一致，跨月日期與站點涵蓋也通過比對。逐時實體表和索引從 36.51 GiB 降到 4.15 GiB，清除舊表後整庫為 17.29 GiB。

API 用相同的單日站點、全網跨日對照、雙站逐時和月工作日查詢比對切換前後。20 併發 120 筆的 p95 從 1.75 秒降到 1.27 秒，40 併發 160 筆從 2.45 秒降到 2.33 秒。280 筆 JSON 回應一致，0 錯誤。另有 82 項 Python 測試通過，含 PostgreSQL 合約測試。

另用 `tools/stress_api.py` 對新啟動的 API 跑 200 筆混合查詢，20 併發下 p95 為 1.25 秒，0 錯誤。切換後整庫使用 `pg_dump -Fc --compress=zstd:3` 串流為 1,455,724,321 位元組（1.36 GiB），匯出耗時 88 秒。此量測無落地備份。

新的月份由 `tools/import_daily.py` 直接寫入 `trip_groups`。`trips` 檢視表會展開原有的逐時站對欄位，保留查詢介面。還留有舊格式的本機部署可用 `python tools/pack_trips.py stage --jobs 3` 建表並逐月核對，完成後用 `publish` 一次切換。驗證失敗時用 `revert` 回到舊表，完全通過後再用 `finalize` 移除舊表。

### 單日全網查詢走 `station_hours` 與持續負載對照（2026-11-19）

單日（或跨日區間）的 `/od/network` 改由既有 `station_hours` 直接彙總各站時段進出量，免除掃描按起訖站對展開的 `trips` 或 `day_flows`。在隔離環境比對 48 組查詢的序列化 JSON 與舊版逐字一致，24 項定向測試全數通過。以 `2026-09-15` 的 07–10 時段為例，`EXPLAIN ANALYZE` 中位數由 `24.141 ms`（掃描 11,934 筆站對）降至 `0.400 ms`（掃描 2,456 筆逐時站點），兩期 Python 分析中位數（不走 API 快取）由 `76.71 ms` 降至 `9.18 ms`。

以本機 13 個真實月份、隔離 PostgreSQL 18.7（`127.0.0.1:55439`）與隔離 API（`127.0.0.1:5519`）進行負載測試：

- **15 秒短階段純單日全網查詢**：舊版在 20 RPS 即開始觸發排隊上限回 `429`（300 筆中 272 筆 `200`、28 筆 `429`，p95 `2,727 ms`），新版在 8、20、40、70 RPS 下皆 0 錯誤，70 RPS 時 `1,050/1,050` 全數回 `200`、p95 `26 ms`。
- **60 秒持續混合查詢（`2 workers` 對照 `3 workers`，CPU 含子孫行程遞迴加總）**：

| --- | ---: | ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `2 workers` | 16 | 16.0 | `200: 960` | 596 ms | 16 | 0.62 | 0.88 | 45.1 ms | 2 | 0 |
| `2 workers` | 24 | 20.8 | `200: 1296, 429: 144` | 2,475 ms | 43 | 0.95 | 1.19 | 49.1 ms | 2 | 0 |
| `2 workers` | 32 | 21.9 | `200: 1364, 429: 556` | 2,499 ms | 43 | 0.94 | 1.14 | 45.8 ms | 2 | 0 |
| `3 workers` | 32 | 30.8 | `200: 1899, 429: 21` | 1,441 ms | 44 | 1.26 | 1.82 | 50.7 ms | 3 | 0 |

**瓶頸與容量判讀**：混合查詢每筆未快取請求的 SQL 執行時間約 `45–51 ms`，且 `pg_temp_blocks` 皆為 `0`、I/O 等待樣本極低（0 至 4 次），代表瓶頸不在磁碟或暫存落盤，而是先卡在 `EXITPULSE_WORKERS` 的並行分析名額（2 個行程理論上限約 `20–22 200/s`，超過後即塞滿 40 筆排隊上限並回 `429`）。在 4 核主機上若需承受 25–30 RPS 以上的未快取混合查詢，可將 `EXITPULSE_WORKERS` 調整為 `3`（正式站預設仍維持 `2`）。

### 查詢引擎效能修復實測（2026-11-25，v1.5.1）

針對 117 個月正式 PostgreSQL 18 資料庫量測三項後端查詢瓶頸並修復，皆於同一台 VPS 與同一資料庫實測前後耗時並比對回應等價性：

1. **全網月檢視跳過站對表**：`Period(daily_totals_only=True)` 原本只對單日生效，導致月份全網查詢（`/api/v1/od/network`）白掃 14,000 筆以上起訖站對 `flows` 或 `trips`。擴充為月檢視亦直接走 `station_hour_flow`／`station_hours` 後，並新增 `_workday_hours()` 處理純工作日加減日。
2. **單日站對逐時直查 `trip_groups`**：`relation_hours_query` 改為先解析站點 ID，並直接以 `WHERE tg.day = %s AND tg.origin = ANY(%s)` 命中 `trip_groups` 主鍵 `(day, hour, origin)` 搭配 `LATERAL unnest`，避免展開其餘 117 站的陣列（無 `trip_groups` 時平滑退回 `trips` 檢視表）。
3. **目錄查詢去除多餘去重**：`get_catalog()` 的 `station_day` 主鍵已為 `(station_id, date)`，移除多餘的 `COUNT(DISTINCT sd.date)` 與關聯子查詢，改以 CTE 預先聚合後再 `LEFT JOIN`。

### 檢視過的效能問題

1. **`localhost` 會慢 2 秒**：Windows 上程式先試 IPv6 的 `::1`，伺服器只綁 `127.0.0.1` 時每個新連線多等約 2 秒。壓測曾因此出現 p50 約 2 秒、連快取命中的目錄查詢也一樣。已把前端代理與測試工具改成 `127.0.0.1`，改後恢復正常。
2. **回應太大**：站對排行約 240 KB，已加 gzip。
3. **每次請求重啟 Python 與重連資料庫**：舊的子行程做法在冷查詢中占 73 至 85% 的時間，現在由常駐行程取代。
4. **前端載入體積**：已將 `maplibre-gl`（6.19.0）與 3D 繪圖拆為延遲載入，Initial bundle 降至約 `743 kB`（零預算警告）。

### 尚未處理

- 開始執行後，分析會占用一個名額直到完成（排隊中若用戶端提前斷線已會在 ASGI 層取消，單一 SQL 敘述則受 `statement_timeout` 限制）。
- 目錄類端點已加上 `ETag` 與 `Cache-Control` 條件式快取（支援 `If-None-Match` 回傳 `304`）。
- 單一 uvicorn 程序處理所有連線，CPU 密集的工作都在分析行程裡，目前不是瓶頸。流量變大時可加 `--workers`，但快取會各自獨立。
