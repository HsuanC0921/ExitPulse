### 資料庫量測

現有 95 個月份 SQLite 共 10.39 GiB，跨月 `ref.sqlite` 為 8.79 MiB。使用 2026-09 真實資料，9 次 SQL 的中位數為逐時 OD 7.86 ms、查單日站點各小時 4.66 ms。獨立 Python 程序跑 9 月 1–5 日的中位數為單站逐時 82 ms、全網逐時 89 ms、全網全天 100 ms。空 Python 程序另外量到 20 ms，完整耗時還包含讀檔、彙總與序列化。

1. 優先處理逐時請求。滑桿現在每次輸入就送出新查詢，舊回應雖不會蓋掉最新畫面，舊程序仍可能佔用資源。先合併拖曳期間的請求並清理取消的程序，再量測當日 24 個時段能否批次傳回。
2. 讓全網逐時直接彙總 `station_hours`。現行先查 OD 站對，再彙總成各站總數。用已匯入的月份對照 `0`、缺資料、站名別名與對照期結果，通過後再考慮採用。
3. 日期索引有小幅收益。將真實 `station_hours` 複製到記憶體，新增 `(date, hour, station)` 後，同一查詢的中位數由 3.08 ms 降至 1.69 ms，2,460 筆結果一致，增加 1.89 MiB。可先保留 SQLite，等批次查詢與快取有實測結果，再評估是否值得對所有月份加索引或開始 PostgreSQL 原型。

對象：`apps/web/src/app/radar.*`，Operate 模式，桌面優先、手機可用。證據來源：原始碼、`impeccable detect` 偵測器、內建瀏覽器在 1113、800、375 寬度的實際畫面，以及使用者提供的 375 寬截圖。

### 偵測器結果

- `border-accent-on-rounded`（radar.css 圖例色塊）：圖例線段用 4px 上框線加圓角，改成實心色塊。

### 優先問題

1. **[P1] 中文斷行不看詞界**（typeset、adapt）：導言、條件摘要、標題句在任何寬度都可能從詞中間斷開。
2. **[P1] 排序依據不透明**（clarify）：列表顯示的數字不是排序依據。
3. **[P1] 篩選與排序不足**（harden）：只有 10 筆，不能搜尋、篩路線、換排序。
4. **[P1] 動畫不表達量**（animate）：光點數量以單組站對內的最大值為 100%，換一組站對就無法比較，且 2.6 秒跑完一趟太快。
5. **[P2] 選取狀態用路線色染底**（polish）：紅色線路的選取列像錯誤。
6. **[P2] 手機觸控目標不足**（adapt）：32px 圖示按鈕。
7. **[P2] 關聯資訊不足**（distill 的反面）：看不到起站整體變化、同起站的其他目的地、一天各時段的分布。
